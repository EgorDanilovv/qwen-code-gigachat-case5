## Сценарий 2: Генерация тестов - Частично работает

**Запрос:** "Напиши unit-тесты для всех функций в calculator.js используя Jest. Тесты должны покрывать как успешные случаи, так и обработку ошибок. Создай файл calculator.test.js с этими тестами."

| Параметр | Значение |
|----------|----------|
| Статус | ⚠️ Частично работает |
| Покрытие функций | 4 из 6 (нет тестов для power и sqrt) |
| Edge cases | частично (есть тесты на деление на 0, но нет на невалидные типы) |
| Синтаксис Jest | корректный |
| Файл создан | ✅ да (calculator.test.js) |
| Тесты запускаются | ❌ нет |

**Проблемы:**
1. Модель сгенерировала тесты только для 4 функций (add, subtract, multiply, divide), отсутствуют тесты для power и sqrt
2. Используется `toThrowErrorMatchingSnapshot()`, что требует snapshot-файлов (которых нет)
3. Тесты на невалидные входные данные не пройдут, т.к. в calculator.js нет проверок типов
4. Модель создала jest.config.js с `preset: 'ts-jest'`, хотя проект на JavaScript (не TypeScript)
5. Попытки запустить тесты завершились ошибкой с кодом -1073741819 (ACCESS_VIOLATION)

**Попытки модели исправить проблему:**
- Создала jest.config.js
- Пыталась разные варианты запуска (с directory, с --config)
- Предложила переустановить зависимости
- Не смогла решить проблему самостоятельно

**Обходное решение:**
- Вручную исправить jest.config.js (убрать preset: 'ts-jest')
- Установить Jest локально: `npm install --save-dev jest`
- Запустить тесты вручную: `npx jest`
- Или попросить модель перегенерировать тесты без snapshot

**Вывод:**
Модель способна генерировать тесты, но не может самостоятельно настроить окружение для их запуска. Требуется ручное вмешательство разработчика.

## Сценарий 3: Генерация документации - Частично работает

**Запрос:** "Напиши полную JSDoc документацию для всех функций в calculator.js. Включи описание параметров, возвращаемых значений и примеры использования."

| Параметр | Значение |
|----------|----------|
| Статус | ⚠️ Частично работает |
| Покрытие функций | 4 из 6 (пропущены power и sqrt) |
| Формат JSDoc | корректный (@param, @returns, @throws) |
| Язык документации | русский ✅ |
| Примеры использования | отсутствуют ❌ |

**Проблемы:**
1. Модель "потеряла" функции `power` и `sqrt` при чтении файла calculator.js
2. Причина - странная проверка "executable" через `type node ./calculator.js`, которая на Windows не работает и, видимо, нарушила контекст
3. Отсутствуют примеры использования (`@example`), хотя были запрошены

**Что сработало:**
- Инструмент `read_file` вызвался корректно
- Формат JSDoc правильный
- Документация для 4 функций сгенерирована качественно

**Обходное решение:**
- Вручную добавить документацию для потерянных функций
- Или попросить модель явно указать все 6 функций в запросе

**Вывод:**
Модель способна генерировать документацию, но может терять контекст при чтении файлов, особенно если выполняются дополнительные shell-команды.

## Сценарий 4: Длинный ответ с кодом и пояснениями - Работает

**Запрос:** "Напиши полный REST API на Express с маршрутами для CRUD операций пользователей (Create, Read, Update, Delete). Включи валидацию входных данных и обработку ошибок. Добавь пояснения к каждому маршруту на русском языке."

| Параметр | Значение |
|----------|----------|
| Статус | ✅ Работает |
| TTFT | ~2-3 сек |
| Общее время | ~40-50 сек |
| Длина ответа | ~80 строк кода + пояснения |
| Streaming | стабильный |
| Код валидный | ✅ да |
| Пояснения | ✅ есть для каждого маршрута |
| Обработка ошибок | ✅ реализована (404, 400) |

**Что сработало:**
- Полный REST API с 5 маршрутами (GET /users, POST /users, GET /users/:id, PUT /users/:id, DELETE /users/:id)
- Валидация входных данных (проверка username/password)
- Обработка ошибок (404 Not Found, 400 Bad Request)
- Комментарии на русском языке
- Подробные пояснения к каждому маршруту
- Код синтаксически корректный

**Незначительные замечания:**
- Используется устаревший пакет `body-parser` (в современном Express встроен `express.json()`)
- Пароли хранятся в открытом виде (но это учебный пример, не production)

**Вывод:**
Модель способна генерировать длинные ответы с кодом и пояснениями. Streaming стабилен на 500+ токенов. Код валидный и готов к использованию.

## Общие выводы

**Сильные стороны GigaChat-2-Max:**
- Стабильный streaming на длинных ответах (500+ токенов)
- Генерация валидного кода с комментариями на русском
- Понимание структуры REST API и CRUD операций
- Способность использовать инструменты (read_file, write_file)

**Слабые стороны GigaChat-2-Max:**
- Может терять контекст при чтении файлов (пропуск функций)
- Проблемы с настройкой окружения для запуска тестов
- Не всегда покрывает все функции при генерации тестов
- Использует устаревшие паттерны (body-parser вместо express.json)

**Рекомендации:**
1. Для генерации тестов явно указывать все функции в запросе
2. Для документации проверять, что модель прочитала весь файл
3. Для запуска тестов требуется ручная настройка окружения
4. GigaChat подходит для базовых задач кодинга, но требует контроля разработчика

**Итог:**
GigaChat-2-Max через gpt2giga прокси **пригоден для использования** как coding assistant, но с ограничениями. Основные проблемы связаны с потерей контекста и настройкой окружения, а не с генерацией кода.
